Production pour `$ARGUMENTS`. **GO mensuel (§1.30)** : un sujet au statut `go-MM/AAAA` (ou `brief validé`) se rédige sans nouvelle demande ; la PR reste le gate. Passe la ligne du plan en `PR ouverte` à l'ouverture de la PR. **La rédaction se fait ici, en session principale** — elle a besoin du contexte complet (brief, voix, first-party). Utilise les skills `article-writer` et `geo-schema` (+ `local-seo` si page locale). Les **vérifications** sont ensuite déléguées à deux subagents en contexte isolé : `fact-checker` puis `contract-checker`.

1. Lis `clients/<slug>/client-brief.md` (+ `nap.md` si local). Si aucun brief de production n'est fourni, exécute d'abord la logique de `/research`.
   - **Relève la version du contrat supportée par le site** (§2 du brief) : elle détermine les composants utilisables. **v1** → `Callout(info/astuce/attention)`, `CTA`, `FAQ` uniquement ; les éléments riches se font en Markdown pur (blockquote attribuée, liste « à retenir », table titrée). **v2** → + `StatGrid`, `ExpertQuote`, `Testimonial`, `ErrorTip`, `Callout(retenir)`. Une version est tout ou rien. **N'utilise jamais un composant hors version** — le build du site casse (comportement voulu).
   - Relève aussi le **porte-parole expert** (et son autorisation de citation) et la **source d'avis clients** : sans eux, pas d'`ExpertQuote` ni de `Testimonial`, même en v2.
2. Rédige le contenu en MDX en respectant intégralement le contrat de la skill `article-writer` : title ~55c, meta ~155c, slug court, intro réponse-directe (~100 premiers mots), structure H2/H3, E-E-A-T, passages auto-suffisants, FAQ (3-6 Q/R), maillage interne (ancres descriptives vers les pages existantes du site), lien(s) externe(s) autoritaire(s), **au moins un élément first-party**, et un **mécanisme de capture** (email, essai gratuit, devis, mini-outil/quiz…) — chaque contenu doit capturer quelque chose, pas seulement informer.
3. Génère le frontmatter complet (avec la `typologie` : actu / guide / evergreen — elle pilote le re-check bimestriel) + le JSON-LD (skill `geo-schema`) : Article/BlogPosting + FAQPage (+ LocalBusiness/Service si page locale, à partir du NAP exclusivement).
4. **Vérification factuelle — délègue au subagent `fact-checker`** (contexte isolé). Fournis-lui le **chemin du fichier de contenu** et le **chemin du dossier client**. Il applique la checklist du skill `fact-check` sans le biais de celui qui vient de rédiger, et te rend un verdict PASS/FAIL. Applique ses corrections : les 🔴 sont bloquants, les **retraits exigés se retirent** (une stat non sourçable ou un `Testimonial` invérifiable sort de l'article — il ne part pas « à confirmer »), les ⚠️ remontent au gate.
5. **Conformité au contrat — délègue au subagent `contract-checker`**. Mêmes entrées. Il contrôle mécaniquement frontmatter, whitelist de la version supportée, capture, FAQ, maillage (et l'existence réelle des cibles), title/meta, H1, absence de style, densité v2, NAP. Applique les corrections localisées qu'il renvoie.
6. **Double PASS obligatoire avant la PR.** Ne passe à l'étape suivante que si `fact-checker` **et** `contract-checker` renvoient PASS.
   - **Relance différenciée** après correction : une correction qui touche **les faits** (chiffre, source, citation, donnée client, NAP) relance le `fact-checker` ; une correction qui touche **la structure** (frontmatter, composants, maillage, title/meta, densité) relance le `contract-checker`. Une correction qui touche les deux les relance tous les deux.
   - Les ⚠️ **non vérifiables** ne bloquent pas, mais se reportent **tels quels** dans le corps de la PR : le gate humain doit savoir ce qui n'a pas pu être contrôlé, sinon il croira le point couvert.
7. Écris le fichier dans le **dépôt du site du client** (chemin local convenu dans le brief), sur la branche `content/<slug>`, commit, push, puis ouvre la PR avec `gh pr create` (ou l'outil de la forge indiqué dans le brief). **Corps de PR** : résumé + rapport `fact-checker` + rapport `contract-checker` + points non vérifiables + checklist post-publication + **la section « ⚠️ Citations à valider »**.
   - **Signalement obligatoire des `ExpertQuote` proposées** : toute citation qui n'est pas reprise d'un first-party du brief est une **proposition**. La lister explicitement (texte exact + à qui elle est attribuée), avec la mention qu'elle doit être **validée par le client avant merge**. Une proposition non validée bloque le merge — elle ne se présente jamais comme une citation acquise.
   - Vérifie les checks (`gh pr checks`) : la validation du frontmatter doit passer. **Ne merge jamais toi-même : je valide (gate).**
   - **Gate de relecture « sans GitHub » (décision d'Axel du 02/11/2026)** : Axel ne va plus chercher l'aperçu ni ne fusionne sur GitHub. Le `detail` du gate dans le tableau de bord porte, dans cet ordre et en mots simples (`docs/lexique-client.md`) : `Aperçu : <URL directe de la PAGE sur l'aperçu Vercel>` (le domaine d'aperçu est dans le commentaire du bot Vercel ou le statut du commit — `gh api repos/<o>/<r>/commits/<sha>/statuses` ; y ajouter le chemin de la page, et vérifier qu'elle répond 200 avec le bon titre ; si l'aperçu n'est pas prêt, `Aperçu : non vérifiable (déploiement en cours)`), puis `Ce qui change :` 3 lignes max, puis `À trancher :` les points ⚠️ formulés en question fermée, puis `Pour publier : répondez « publie <n° de PR> », ou « <n° de PR> : <correction> »`. Le résumé matinal reprend ces champs tels quels et c'est en réponse au résumé (ou dans la discussion KAELIX) qu'Axel valide.
   - **Après ton push du repo marketing**, vérifie que `origin/main` contient ton commit (`git log origin/main -1`) : si la session a poussé sur une branche de travail (`claude/…`), fusionne-la en avance rapide dans `main` ; sinon la prochaine exécution relira l'ancien statut et refera le sujet.
8. Après ma validation (« publie <n° de PR> », écrite par Axel dans la conversation, jamais déduite) : déroule la checklist post-publication — merge (fusion par `gh api … /merge`, faite par la session sur cette instruction explicite ; sur « <n° de PR> : <correction> », appliquer la correction sur la branche, relancer le vérificateur concerné, pousser, redonner l'aperçu, et attendre le « publie »), déploiement, présence dans le sitemap, puis **automatiquement** : `node scripts/gsc-fetch.mjs inspect <url>` (état d'indexation) et `request-indexing <url>` (⚠️ Indexing API officiellement limitée aux pages JobPosting/BroadcastEvent — le script tente et affiche le caveat ; si l'inspection montre l'URL non découverte après quelques jours, le bouton de l'interface GSC reste la voie sûre, à signaler dans la to-do opérateur), et **ne pas toucher le contenu pendant 90 jours** (Google teste ; la position moyenne n'est fiable qu'à J90).
9. Ajoute la ligne dans `clients/<slug>/tracking.md` (date de publication, type, mot-clé, URL, typologie, **persona**, statut). Si le contenu vient d'un sujet de `content-plan.md`, passe aussi sa ligne du plan en statut `publié`.
